在 Rock 5B 上从源码构建 Neovim 并配置 LazyVim ​

记录一次完整的搭建过程:aarch64 开发板、Debian 12、源码编译 Neovim 0.12.5, 以及途中踩到的三个不查源码根本找不到原因的坑。

  • 三、装上 LazyVim
  • 四、第一个坑:Mason 的架构识别

一、先说网络 ​

这一节把网络问题一次讲完,后面不再重复。

本机在国内网络环境,GitHub 直连不通——curl https://github.com 超时,git clone 直接失败。 代理跑在手机热点的网关上(http://172.20.10.1:1082),不是本机。

因为代理只在连着那个热点时有效,我在 ~/.zshrc 里加了带网段守卫的导出, 避免换网络之后一个失效的代理把所有 git/npm/curl 都拖死:

zsh
# --- 代理（仅手机热点 172.20.10.x 生效） ---
if ip -4 -o addr show scope global 2>/dev/null | grep -q '172\.20\.10\.'; then
    export https_proxy=http://172.20.10.1:1082
    export http_proxy=http://172.20.10.1:1082
    export all_proxy=http://172.20.10.1:1082
fi

这个守卫很重要。不加的话,离开热点后 git clone 会挂在一个连不上的代理上超时, 报错信息还完全看不出是代理的问题。

几个补充事实:

  • CMake 下载第三方依赖走 libcurl,会读 http_proxy/https_proxy,所以编译前导出环境变量即可, 不需要去改 cmake.deps/deps.txt 里的 URL。
  • api.github.com 即使走代理也返回 403(共享出口 IP 被限流)。需要查仓库版本时改用 https://github.com/<owner>/<repo>/releases.atom,atom feed 不受 API 限流影响。
  • 备用通道 https://ghproxy.net/https://github.com/... 可以直连透传,不需要代理。
  • 手机热点拉大文件经常被截断,一律加 curl -C - 断点续传。
  • 各语言包管理器都已配好国内镜像(pip → 清华、npm → npmmirror、cargo → rsproxy、apt → USTC), 这些通常不需要代理。

好了,网络的事到此为止。

二、构建 Neovim ​

为什么不用 apt ​

Debian 12 源里的 Neovim 是 0.7 时代的版本,而现在的插件生态(LazyVim 15.x、nvim-treesitter main 分支) 要求至少 0.11.2。所以必须自己编译。

为什么选 0.12.5 而不是稳妥的 0.11.x ​

一般直觉是"选旧一版更稳",但这里反了。原因是 LazyVim 的 treesitter 配置里有这么一行 (lazyvim/plugins/treesitter.lua):

lua
commit = vim.fn.has("nvim-0.12") == 0 and "7caec274fd19c12b55902a5b795100d21531391f" or nil,

意思是:Neovim 低于 0.12 时,会被钉在一个旧 commit 上。所以 0.12+ 反而能拿到最新的 treesitter 生态。确认了这点之后,直接上最新稳定版 v0.12.5。

一个省事的发现:不需要 gettext,也就不需要 root ​

从源码编译 Neovim 的文档里,gettext(msgfmt)是列为必需的。但本机没装 msgfmt, 而 apt 装包需要密码。抱着试试看的心态翻了源码,发现 src/nvim/po/CMakeLists.txt 开头是:

cmake
option(ENABLE_TRANSLATIONS "Localizations to build" OFF)
if(NOT ENABLE_TRANSLATIONS)
  return()
endif()

find_package(Gettext REQUIRED)

默认就是 OFF,而且直接 return 了。也就是说那句 find_package(Gettext REQUIRED) 根本不会被执行到——默认构建不需要 gettext。

结论:整个编译过程不需要任何 root 权限,只有最后 make install 到 /usr/local 需要。 如果当初直接照文档去折腾 gettext,会白白多绕一大圈。

构建 ​

bash
cd ~/Applications
git clone --depth 1 --branch v0.12.5 https://github.com/neovim/neovim.git
cd neovim

# 代理导出见上一节，这里不重复
make CMAKE_BUILD_TYPE=Release
sudo make install

用 Release 而不是默认的 Debug——这是一台 8 核 ARM 开发板,要的是运行时的编辑体验, 不是调试 Neovim 自身。

构建产物 build/bin/nvim 在安装前就能试跑,但要注意未安装时必须指定 runtime 路径:

bash
VIMRUNTIME=runtime ./build/bin/nvim --version

不设 VIMRUNTIME 会报 module 'vim.uri' not found 之类的错——那不是构建失败,只是找不到 runtime。

三、装上 LazyVim ​

bash
git clone https://github.com/LazyVim/starter ~/.config/nvim
rm -rf ~/.config/nvim/.git    # 去掉 starter 的 git 历史，方便自己管理

LazyVim 的扩展机制是 extras,不需要自己写语言配置,在 lua/config/lazy.lua 的 spec 里 import 进来就行:

lua
spec = {
  { "LazyVim/LazyVim", import = "lazyvim.plugins" },

  -- 语言支持
  { import = "lazyvim.plugins.extras.lang.python" },     -- Python
  { import = "lazyvim.plugins.extras.lang.typescript" }, -- Node / JS / TS
  { import = "lazyvim.plugins.extras.lang.clangd" },     -- C / C++
  { import = "lazyvim.plugins.extras.lang.rust" },       -- Rust
  { import = "lazyvim.plugins.extras.lang.json" },
  { import = "lazyvim.plugins.extras.lang.markdown" },
  { import = "lazyvim.plugins.extras.lang.yaml" },
  { import = "lazyvim.plugins.extras.lang.toml" },
  { import = "lazyvim.plugins.extras.lang.git" },
  { import = "lazyvim.plugins.extras.lang.docker" },
  { import = "lazyvim.plugins.extras.lang.sql" },
  { import = "lazyvim.plugins.extras.lang.nushell" },

  -- 格式化 / 检查 / 调试
  { import = "lazyvim.plugins.extras.formatting.prettier" },
  { import = "lazyvim.plugins.extras.linting.eslint" },
  { import = "lazyvim.plugins.extras.dap.core" },

  { import = "plugins" },
},

有几点值得注意:

  • XML 没有官方 extra。我翻了 lazyvim/plugins/extras/lang/ 目录,有 python、rust、typescript、 clangd、json、markdown、yaml、toml……唯独没有 xml。需要手写,见 第六节。
  • Bash/Shell 也不需要 extra,LazyVim 核心自带 bashls + shfmt。
  • SQL extra 并不装 sqls。它用的是 vim-dadbod + sqlfluff,我一开始想当然地 去装 sqls,后来读源码才发现装了个没用的东西。

语言 extras 自带 LSP 声明,LazyVim 会把 opts.servers 里的服务自动交给 Mason 安装—— 这个机制在 lazyvim/plugins/lsp/init.lua 里:

lua
local install = vim.tbl_filter(configure, vim.tbl_keys(opts.servers))
if have_mason then
  require("mason-lspconfig").setup({
    ensure_installed = vim.list_extend(install, ...),

看起来很省心,但正是这个"自动"引出了接下来最大的一个坑。

四、第一个坑:Mason 的架构识别 ​

现象 ​

首次 :Lazy sync 之后,Mason 装了 20 个包,然后卡住了。

没有报错,没有网络活动,staging 目录是空的,进程 CPU 0%。就是不动。

缺的是这几个:clangd、codelldb、lemminx、sqls、debugpy、stylua。

排查 ​

一个包一个包单独装,发现 stylua 单独装也挂——不是队列被前面的包堵住,是这些包自己装不了。

于是去看 mason-registry 的数据。registry 就缓存在本地:

~/.local/share/nvim/mason/registries/github/mason-org/mason-registry/registry.json

写个脚本把可疑包的资产目标打出来:

python
import json
reg = {p["name"]: p for p in json.load(open("registry.json"))}
for n in ["stylua", "clangd", "lemminx", "marksman", "taplo"]:
    assets = reg[n]["source"].get("asset", [])
    print(n, [a.get("target") for a in assets])

结果一目了然:

stylua    [... 'linux_x64_gnu', 'linux_arm64_gnu', 'linux_x64' ...]     ← 只有 _gnu
clangd    ['darwin_x64', 'darwin_arm64', 'linux_x64_gnu', 'win_x64']    ← 压根没有 arm64
lemminx   [... 'linux_x64_gnu', 'linux_arm64_gnu', ...]                 ← 只有 _gnu
marksman  [... 'linux_x64', 'linux_arm64', ...]                         ← 不带 _gnu，能装 ✅
taplo     [... 'linux_x64', 'linux_arm64', ...]                         ← 不带 _gnu，能装 ✅

Mason 把本机平台识别成了 linux_arm64(不带 _gnu 后缀),而 stylua/lemminx/codelldb 只提供 linux_arm64_gnu 资产,匹配不上;clangd 更是根本没有 aarch64 版本。

而 Mason 匹配失败时不触发回调,整个安装队列静默挂起——这就是"卡住却不报错"的原因。

判断方法 ​

现在遇到 Mason 装包卡住,我会先查这个包在 registry.json 里的 source.asset[].target:

  • 有不带 _gnu 的 linux_arm64 → 能装
  • 只有 linux_arm64_gnu → 装不了
  • 只有 linux_x64* → 完全没戏

这个线索比看日志快得多。

处理 ​

  • 能换就换:sqls 是 pkg:golang 源(需要 Go 工具链),换成 npm 版的 sqlls 即可。 后来发现 LazyVim 的 SQL extra 压根不用 LSP,索性去掉。

  • 该手动就手动:clangd 走 apt,codelldb/lemminx/lazygit 手动下载。

  • 让 Mason 别再重试:已经手动装好的包,给 $MASON/packages/<name>/mason-receipt.json 写一份凭据,Mason 就认为它已安装。 照抄一个正常装好的包的格式即可:

    json
    {
  "links": { "bin": { "codelldb": "extension/adapter/codelldb" }, "share": {}, "opt": {"lldb": "extension/lldb"} },
  "name": "codelldb",
  "source": { "type": "registry+v1", "id": "pkg:github/vadimcn/vscode-lldb@v1.12.3", "raw": {...} },
  "schema_version": "2.0"
}

    不这么做的话,每次启动 Neovim 都会重试一遍、再挂一遍。

  • LSP 类的换另一种写法:在 nvim-lspconfig 的 opts 里关掉 Mason 托管,直接用 PATH 里的:

    lua
    {
  "neovim/nvim-lspconfig",
  opts = { servers = { clangd = { mason = false } } },
}

五、第二个坑:tree-sitter CLI 的 GLIBC 版本 ​

LazyVim 15.x 用的是 nvim-treesitter 的 main 分支,而这个分支编译 parser 需要 tree-sitter CLI(要求 ≥ 0.26.1,并且明确不能用 npm 版)。LazyVim 会通过 Mason 自动兜底安装它。

装是装上了,但所有 parser 编译全部失败:

[nvim-treesitter/install/cpp] error: Error during "tree-sitter build":
  tree-sitter: /lib/aarch64-linux-gnu/libc.so.6:
  version `GLIBC_2.39' not found (required by tree-sitter)

Mason 提供的那份预编译 tree-sitter 是在 Ubuntu 24.04 上构建的,要求 GLIBC 2.39; 而 Debian 12 只有 GLIBC 2.36。

这类"预编译二进制要求的 glibc 比目标系统新"的问题在 ARM 上特别常见,因为上游 CI 基本跑在 更新的发行版上。

解决办法相当直接——用 cargo 从源码编译,编出来的二进制自然链接本机 glibc:

bash
cargo install tree-sitter-cli     # → ~/.cargo/bin/tree-sitter

耗时约 2 分半,产物 v0.27.0。

然后有个细节:得把 Mason 那份坏的删掉,否则它在 mason/bin 里会抢在 PATH 前面:

bash
rm -f ~/.local/share/nvim/mason/bin/tree-sitter
rm -rf ~/.local/share/nvim/mason/packages/tree-sitter-cli

(当然,也要把自己配置里 ensure_installed 的 tree-sitter-cli 去掉,不然它又装回来了。)

删干净后重新编译 parser:

vim
:TSInstall! python typescript tsx javascript c cpp rust markdown markdown_inline
        \ json xml dtd yaml toml lua vim vimdoc bash dockerfile sql

结果:Installed 22/22 languages。之前 0 个,现在全过。

中途还有个小插曲:TSUpdate 会报 "All parsers are up-to-date" 但实际一个 parser 都没有。 用带感叹号的 TSInstall! 强制装才对。

后记:一个我自己挖出来的坑 ​

这一节是装完之后才发生的,但和上面同一套东西,接在这里讲最顺。

某天打开 nvim,报:

[nvim-treesitter/install/gitcommit] error: Error during "tree-sitter..."
Caused by: Lock file '/home/radxa/.cache/tree-sitter/lock/gitcommit-d6908a35...'
建议:If there isn't another concurrent tree-sitter instance, remove it...

锁文件是哪里来的。 tree-sitter CLI 用 ~/.cache/tree-sitter/lock/ 下的锁文件防止 并发编译同一个 parser。而我在前面排查那些问题的过程中,用过超时和 pkill 强杀 headless 的 nvim —— 被强杀的 nvim 所派生的 tree-sitter build 子进程会被 init 收养(PPID 变成 1), 它自己还继续跑,锁也不释放。之后任何 nvim 想编译同一个 parser 都会撞锁。

所以别急着删锁。 报错里那句 "If there isn't another concurrent tree-sitter instance, remove it" 的前提是"确实没有并发实例",得先确认:

bash
ps -o pid,ppid,etime,time,pcpu,cmd -p <pid>

两个字段是关键:

  • PPID = 1 → 父进程已死,是孤儿,可以安全清理
  • %CPU 接近 100 且 TIME 很大 → 它在真干活,不是在等锁

我那三个进程:PPID=1、ELAPSED 17分48秒、TIME 18分02秒、CPU 99.3% —— 孤儿, 而且正满负荷跑着。如果是活着的 nvim 在编译,删锁只会制造新的问题。

然后发现了更离谱的事。 它编译的是 gitcommit 的 parser,而那个 parser.c 有 89131 行。tree-sitter 生成的语法分析器都是巨型 C 文件(塞满了巨大的状态转移表), GCC 在 -O2 下优化它慢得病态——已经烧掉 18 分钟 CPU 还没结束。

实测对比:

优化级别耗时
-O2(tree-sitter CLI 默认)> 18 分钟(仍未跑完)
-O1(手动编译)11.8 秒

差了近百倍。这跟前面那个 GLIBC 的坑其实是同一类问题: 在 ARM 开发板上,编译 tree-sitter 相关的东西代价往往被严重低估。

处理。 既然孤儿进程编完了也没人要,直接手动用低优化级别编好丢进 parser 目录:

bash
SRC=~/.cache/nvim/tree-sitter-gitcommit/src
DST=~/.local/share/nvim/site/parser
cc -O1 -fPIC -std=c11 -I "$SRC" -shared -Wl,--no-undefined \
   "$SRC/parser.c" "$SRC/scanner.c" -o "$DST/gitcommit.so"

kill -TERM <tree-sitter pid> <cc pid> <cc1 pid>   # 三个都要杀，杀父进程不会带走子进程
rm -f ~/.cache/tree-sitter/lock/*.lock

nvim 起来就能用,get_installed() 也认得它,不会再触发重编。

教训。 这是整个过程中唯一一个自己造出来的坑——前面那些都是环境给的, 这一个是我用 kill -9 和超时强杀 nvim 造成的。后台正在编译东西的时候,让它自己跑完, 比事后去清孤儿进程和死锁省事得多。

六、第三个坑:那些装不上的组件 ​

codelldb 和它的隐藏路径要求 ​

codelldb 是 C/C++/Rust 的调试适配器。从 GitHub release 下 codelldb-linux-arm64.vsix (就是个 zip),解压出来是 extension/adapter/codelldb 和 extension/lldb/lib/liblldb.so。

装的时候要注意 LazyVim 对它的两处不同定位方式:

C/C++(clangd.lua)——通过 PATH 查找:

lua
executable = { command = "codelldb", args = { "--port", "${port}" } },

Rust(rust.lua)——硬编码了 Mason 的路径:

lua
local codelldb = vim.fn.exepath("codelldb")
local library_path = vim.fn.expand("$MASON/opt/lldb/lib/liblldb" .. codelldb_lib_ext)

所以除了把 codelldb 放进 PATH,还得把 liblldb.so 软链到 $MASON/opt/lldb/lib/liblldb.so,否则 Rust 调试起不来。

bash
MASON=~/.local/share/nvim/mason
mkdir -p "$MASON/packages/codelldb"
cp -r extension "$MASON/packages/codelldb/extension"
ln -sf "$MASON/packages/codelldb/extension/adapter/codelldb" ~/.local/bin/codelldb
mkdir -p "$MASON/opt/lldb/lib"
ln -sf "$MASON/packages/codelldb/extension/lldb/lib/liblldb.so" "$MASON/opt/lldb/lib/liblldb.so"

注意:从 zip 解压出来的 codelldb 丢失了可执行位,需要 chmod +x,否则报"权限不够"。

XML:需要手写的那个 ​

LazyVim 没有 xml extra,所以要自己写一个 plugin spec。关键是 mason = false:

lua
-- ~/.config/nvim/lua/plugins/xml.lua
return {
  {
    "nvim-treesitter/nvim-treesitter",
    opts = { ensure_installed = { "xml", "dtd" } },
  },
  {
    "neovim/nvim-lspconfig",
    opts = {
      servers = {
        lemminx = { mason = false },   -- Mason 那份装不了，用手动装的
      },
    },
  },
}

其余手动装的 ​

组件来源说明
clangdsudo apt install clangd版本 14,与已装的 clang 14 一致
lemminxGitHub release zipXML LSP
lazygitGitHub release不在 mason registry 里,<leader>gg 依赖它

debugpypip install debugpyPython 调试器

Python 调试器这里还改了一处 LazyVim 的默认配置。它默认写的是:

lua
require("dap-python").setup("debugpy-adapter")   -- 依赖 Mason 提供 debugpy

而本机 debugpy 是 pip 装进系统 python 的,所以改成直接指向 python3:

lua
{
  "mfussenegger/nvim-dap-python",
  config = function()
    require("dap-python").setup(vim.fn.exepath("python3"))
  end,
}

七、中文相关的配置 ​

中文用户的痛点主要是两个:输入法吞按键,和编码乱码。

输入法自动切换 ​

在插入模式用中文输入法打字,按下 Esc 回普通模式之后,输入法还是中文状态—— 这时候按 j/k/dd 全被输入法吃掉了,得手动切一下才能用。

先确认本机是哪个输入法:

bash
fcitx --version     # fcitx version: 4.2.9.9
command -v fcitx-remote    # 有
command -v fcitx5-remote   # 没有

是 fcitx 4,不是 fcitx5。这点很关键——网上大量教程用的是 fcitx5-remote, 在 fcitx 4 上根本不存在。所以用 fcitx-remote:

lua
-- ~/.config/nvim/lua/plugins/chinese.lua
local ime = "fcitx-remote"
if vim.fn.executable(ime) == 1 then
  vim.api.nvim_create_autocmd({ "InsertLeave", "CmdlineLeave" }, {
    group = vim.api.nvim_create_augroup("ChineseIMEReset", { clear = true }),
    callback = function()
      vim.fn.jobstart({ ime, "-c" }, { detach = true })   -- -c = 切回英文
    end,

end

用 jobstart 异步调用而不是 vim.fn.system,避免每次离开插入模式都卡一下。

八、验证 ​

配置写完不能只看"启动没报错",得逐个文件类型实测 LSP 到底挂上没。

思路是 headless 打开每种文件,等 LSP 客户端 attach,然后打印状态:

lua
for _, c in ipairs(cases) do
  vim.cmd("edit " .. c.file)
  local buf = vim.api.nvim_get_current_buf()

  vim.wait(45000, function()
    return #vim.lsp.get_clients({ bufnr = buf }) > 0
  end, 300)

  local names = vim.tbl_map(function(x) return x.name end, vim.lsp.get_clients({ bufnr = buf }))
  local hl = vim.treesitter.highlighter.active[buf] ~= nil
  print(c.ft, "ts_hl=" .. tostring(hl), "LSP=[" .. table.concat(names, ",") .. "]")
end

九、总结 ​

回头看,这次搭建体力活不多,难的都在诊断上。三个坑的共同点很一致:

1. 失败是静默的。 Mason 匹配不上架构时不报错,只是不回调、卡住;TSUpdate 会谎报 "up-to-date"; pyright 慢启动被我误判成配置错误。这三件事都没有给出指向真正原因的报错。

2. 答案在源码/数据里,不在文档里。

  • ENABLE_TRANSLATIONS 默认 OFF 这件事,只写在 src/nvim/po/CMakeLists.txt 里, 而构建文档把 gettext 列为必需——照着文档做就会白折腾。
  • Mason 的架构匹配规则,只能靠读 registry.json 的 asset[].target 才能看出来。
  • LazyVim 对 codelldb 的两套定位方式(C/C++ 走 PATH,Rust 走 $MASON/opt/lldb/...), 分别写在 clangd.lua 和 rust.lua 两处,不读就不知道为什么要软链那个 .so。
  • SQL extra 不用 sqls 而是用 dadbod + sqlfluff,也是读源码才知道的。

3. "预编译二进制"和"编译开销"在 ARM 上都要格外警惕。 tree-sitter CLI 卡在 GLIBC 2.39 vs 2.36 上。ARM 生态里上游 CI 普遍跑在新发行版上, 预编译产物对 glibc 的要求经常高于目标系统,遇到"二进制跑不起来"先 ldd --version 对比, 能用 cargo install / 源码编译解决的就直接编。反过来,"源码编译"也不等于便宜: 同一个 parser.c,-O2 要 18 分钟以上、-O1 只要 12 秒,差距近百倍。 遇到编译长时间不结束,先怀疑优化级别,别干等。

4. 后台在跑的构建,让它跑完。 唯一一个自己造出来的坑:kill -9 / 超时强杀 nvim,导致 tree-sitter 的编译子进程变成孤儿、 锁文件不释放,后续每次编译都撞锁报错。前面三个坑都是环境给的,这一个纯粹是操作不当。 要中断长时间编译,先想想它会不会留下状态。

最后一次 :checkhealth 干净,记录在此。整个过程的详细配置说明放在 ~/.config/nvim/SETUP.md,以后改配置前先看那个。
