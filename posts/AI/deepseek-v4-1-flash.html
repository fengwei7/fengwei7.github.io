DeepSeek V4.1 Flash 深度拆解：CED、CSA2 与 890 字节/token 的 KV Cache 极限 ​

一句话总结：DeepSeek V4.1 Flash 的真正看点不是“又一个 MoE”，而是把 KV Cache 当成一等公民：在表示、序列、层、系统四个层面同时压缩，再用训练和推理基础设施把这种压缩变成可部署的成本优势。

2026 年 9 月 10 日，DeepSeek 发布 V4.1 Flash。官方给它的定位很直接：更强、更快、更普惠。从技术报告看，这不是 V4 的简单复刻，而是一次相当激进的“非对称架构”实验：

  • 552B 语言骨干 + 196B Engram[10] 参数，但 prefill 每 token 只激活 8B，decode 激活 16B；
  • 原生支持 1M token 上下文和多模态输入；
  • 常驻 HBM 的 global KV Cache 压到 890 B/token，约为 V4-Flash 的 1/4；
  • 持久化 KV Cache 约为 V4-Flash 的 1/8；
  • 相比初代 DeepSeek-V1，每 token 的 global KV 只有约 1/437。

本文写作时，线上最新版本是 2026 年 10 月 17 日发布的 V4.1-Flash-1017[3]。新版本主要提升了 Agent 与“从零构建项目”的能力；由于 1017 发布说明没有给出新的架构细节，下文仍以 9 月技术报告为主要依据。

本文基于 V4.1 Flash 技术报告[1]、官方发布说明[2]，以及 DeepSeek-V4[4]、V3.2[5]、V3[7]、V2[6] 的公开论文，回答三个问题：

  1. CED 是怎么把 prefill 计算量砍掉近一半的？
  2. CSA2 + FP4 是怎么把 KV Cache 压到 890 B/token 的？
  3. DeepSeek 的 KV Cache 优势，到底“独”在哪里？

阅读提示：只想看结论，可以直接跳到第 6、9、11 节；想看架构细节，按顺序读第 2–5 节；想看训练，读第 8 节。文中 benchmark 均为厂商报告，未做独立复现；890 B 等核心数字来自论文。

1. Agent 时代，为什么 KV Cache 成了主角 ​

过去几年，大模型推理优化的主线是“把权重压小、把矩阵乘加快”。但到了长程 Agent 场景，矛盾变了。

一个 Agent 任务往往包含几十到几百轮工具调用：读文件、跑命令、看报错、改代码、再跑测试。每一轮的工具输出都会追加到上下文里，下一轮 decode 时，模型要对整个前缀做注意力。于是出现三个瓶颈：

瓶颈具体表现受什么影响
HBM 容量每个并发请求都要占一份 KV Cache，长上下文时单请求可达 GB 级层数 × 序列长度 × KV 头数 × 维度 × 精度
HBM 带宽decode 每生成一个 token，都要把历史 KV 读一遍KV 字节数 × 读取频率
SSD / 主机带宽多轮对话要复用前缀缓存，缓存命中时要搬大量 KV持久化 KV 大小、缓存命中率、I/O 带宽

这也是为什么 V4.1 技术报告在开篇就把 prefill 成本、KV 存储、数据传输带宽列为主要瓶颈。在 Agent 负载里，输入往往远长于输出，prefill 和缓存命中成本会主导账单；如果 KV Cache 太大，既压低了并发，又让前缀缓存变得不划算。

一个最朴素的 KV 大小公式是：

KVbytes=L×N×Hkv×dh×b×2\text{KV}_{\text{bytes}} = L \times N \times H_{kv} \times d_h \times b \times 2 KV​bytes​​=L×N×H​kv​​×d​h​​×b×2

其中 LLL 是层数，NNN 是 token 数，HkvH_{kv}H​kv​​ 是 KV 头数，dhd_hd​h​​ 是头维度，bbb 是每个元素的字节数，最后的 2 表示 K 和 V 各一份。这个公式里的每一项，后来都成了 DeepSeek 的优化对象：

  • Hkv×dhH_{kv} \times d_hH​kv​​×d​h​​：用 MLA（V2/V3）或 shared-KV MQA（V4.1）把 K/V 压成低秩 latent / 单 head 表示，而不是按头存全量；
  • NNN：用 CSA/HCA 把每 mmm 个 token 压成一个 entry；
  • LLL：用 CSA2 的跨层共享，让大多数层复用少数 Full 层的 KV；
  • bbb：用 FP8/FP4 量化，把每个值从 16 bit 压到 8 bit、4 bit；
  • 缓存生命周期：把 global KV 和 SWA KV 分开，分别放在 HBM、主机内存和 SSD。

关键认知：MoE 解决的是“参数容量大、计算量小”，但它不解决 KV Cache。KV 的大小只跟注意力层数、序列长度、头数、维度和精度有关。V4.1 的 552B 总参数、8B/16B 激活，是 MoE 的功劳；890 B/token 则是注意力和缓存设计的功劳。两者必须同时成立，模型才能既聪明又便宜。

2. 全局架构：两个 20 层的“半模型” ​

V4.1 Flash 的语言骨干只有 40 层，但被切成了两个 20 层的部分：

  • Causal Encoder（20 层）：负责读输入，生成全局表示；
  • Decoder（20 层）：负责生成输出，但它的 global KV 不再由自己逐层计算，而是从 Encoder 最后一层投影出来。

整体结构可以粗略画成这样：

text

2.1 为什么 prefill 8B、decode 16B？ ​

这是 V4.1 最容易被误解的地方。它不是说模型有两套权重，而是说prefill 和 decode 走不同的计算路径：

  • Prefill：大部分 prompt token 只需要经过 20 层 Encoder，就能得到 decoder 所需的 global KV；decoder 只对最后 128 个 token 做 SWA 重放。因此每 token 的有效激活参数约为 8B。
  • Decode：每生成一个 token，都要跑完整的 40 层（Encoder + Decoder），所以每 token 激活约为 16B。

这正好对应 Agent 负载的特征：输入重、输出轻。prefill 便宜，意味着长工具输出、长文档、长代码库的读取成本低；decode 贵一些，但输出 token 少，总成本仍然可控。

这不是“把 40 层砍成 20 层”，而是把 prefill 和 decode 的计算图解耦：prefill 只跑 Encoder，decode 才跑完整模型。

2.2 MoE 与注意力的分工 ​

V4.1 沿用 DeepSeekMoE[7]：1 个共享 expert 保证通用能力，384 个细粒度 routed expert 提供容量，每 token 只激活 6 个。这样总参数可以很大，单 token 的 FFN 计算量却很小。

但 MoE 只优化 FFN，不优化注意力。真正决定长上下文成本的是 CSA2 和 KV Cache。第 3 节先看 CED 如何让 prefill 只跑一半。

2.3 两个容易被忽略的组件：Single-Pass mHC 与 Engram ​

除了 CED 和 CSA2，V4.1 还有两个不直接压 KV、但影响训练与部署成本的组件。

Single-Pass mHC[9] 是对 V4 中 mHC 残差流混合的改造。mHC 在相邻 Transformer block 之间维护 nnn 条残差流，表达力更强，但原始的多趟实现需要反复读写激活。V4.1 把输入混合系数错开一个 block，使每个 block 使用上一 block 产生的系数，从而消除输入混合对当前 block 系数归约的依赖：常规两趟实现要读写 (3n+2)d(3n+2)d(3n+2)d 个激活，现在只需 (2n+2)d(2n+2)d(2n+2)d；相对原始四 kernel 实现 (4n+4)d(4n+4)d(4n+4)d，配合 Mega-mHC kernel 后激活访存减半。它不改变 KV 大小，但对 1M 序列的训练和 decode 带宽很关键。

Engram[10] 则是 196B 参数的条件记忆模块：用 n-gram hash 查表，把“记忆”从 FFN 计算中解耦出来。它分成两个模块，放在第 1 和第 14 层（零索引），embedding 表和 K/V 投影都用 FP8 存储；推理时可以按 token 序列确定性地预取。Engram 不进入 KV Cache，但它是“552B 骨干 + 196B Engram”这个参数账本的另一半。

3. CED：把 Decoder 的全局 KV“投影”出来 ​

3.1 从 YOCO 说起 ​

V4.1 的 Causal Encoder-Decoder（CED）受到 YOCO[8] 的启发。YOCO 的核心思想是：只缓存一次。它把模型分成 self-decoder 和 cross-decoder，只让 self-decoder 生成并缓存全局 KV，cross-decoder 直接复用这份 KV，从而把需要独立存储 KV 的层数从 LLL 降到 L/2L/2L/2。

CED 继承了这个思路，但做了两点关键改动：

  1. 不是简单的 cross-attention 复用，而是用层特定的投影矩阵，从 Encoder 最后一层隐藏状态生成 Decoder 的 global KV；
  2. SWA 仍然逐层计算，保留每一层的局部建模能力，避免 Decoder 变成“只会读全局摘要”的浅层网络。

3.2 公式与直觉 ​

对于第 lll 个 Decoder 层（l>L/2l > L/2l>L/2），CED 把它的 global KV entry ClC_lC​l​​ 和压缩权重 ZlZ_lZ​l​​ 定义为不再来自自己的隐藏状态 HlH_lH​l​​，而是：

Cl=HL/2WlKV,Zl=HL/2WlZ,l>L2C_l = H_{L/2} W_l^{KV}, \qquad Z_l = H_{L/2} W_l^{Z}, \qquad l > \frac{L}{2} C​l​​=H​L/2​​W​l​KV​​,Z​l​​=H​L/2​​W​l​Z​​,l>​2​​L​​

其中 HL/2H_{L/2}H​L/2​​ 是 Encoder 最后一层的隐藏状态，WlKVW_l^{KV}W​l​KV​​ 和 WlZW_l^{Z}W​l​Z​​ 是层特定的投影矩阵。结合 CSA2 后，Decoder 只有 Full 层会真正物化这份 KV，Reindex/Reuse 层直接复用。

这个设计的直觉是：

  • 全局 KV 是“对上下文的摘要”，不一定非要由每一层自己重新计算。Encoder 已经读完了整个 prompt，它的最后一层隐藏状态包含了足够丰富的上下文信息。
  • Decoder 的 query 仍然是逐层独立的。每一层用自己的 Q 去读由 HL/2H_{L/2}H​L/2​​ 投影出的 global KV（Decoder 内由唯一的 Full 层物化，其余层共享），再加自己的 SWA 局部 KV，因此层间的表达深度没有丢。
  • SWA 逐层保留，让 Decoder 仍然能处理局部语法、指代、格式等细粒度依赖。

3.3 计算量：从 O(NL) 到 O(NL/2) ​

对于长度 N≫nwinN \gg n_{\text{win}}N≫n​win​​ 的序列，按“每 token 要经过多少层”计，标准 Transformer 的 prefill 需要跑完 LLL 层，论文记作 O(NL)O(NL)O(NL)。CED 只需要：

  • 跑完 L/2L/2L/2 层 Encoder；
  • 对最后 nwinn_{\text{win}}n​win​​ 个 token 跑 L/2L/2L/2 层 Decoder，用于生成 Decoder SWA KV。

因此：

O(NL)→O(NL2+nwinL2)≈O(NL2)O(NL) \;\rightarrow\; O\left(\frac{NL}{2} + n_{\text{win}}\frac{L}{2}\right) \approx O\left(\frac{NL}{2}\right) O(NL)→O(​2​​NL​​+n​win​​​2​​L​​)≈O(​2​​NL​​)

当 NNN 远大于窗口（V4.1 的 nwin=128n_{\text{win}}=128n​win​​=128）时，第二项可以忽略，prefill 计算量接近减半。这就是 8B vs 16B 的来源。

3.4 代价是什么？ ​

CED 不是免费的午餐。它把 Decoder 的 global KV 与 Decoder 自身的隐藏状态解耦，意味着：

  • Decoder 不能通过“改写 global KV”来影响全局记忆，只能通过自己的 Q 去读取；
  • global KV 的质量高度依赖 Encoder 最后一层的表示；
  • SWA 需要额外的重放机制，否则 Decoder 的局部 KV 不完整。

DeepSeek 的解法是 Decoder SWA Bounded Replay：每次 prefill 只重放 prompt 最后 nwinn_{\text{win}}n​win​​ 个 token，把它们过一遍 Decoder，得到用于首批 decode 的 SWA KV；这份 KV 只用于解码，不写入前缀缓存。这样既补上了局部状态，又不会把 prefill 重新拉长。

一句话：CED 把“全局记忆”变成 Encoder 的一次性投影，把“局部记忆”留给每层 SWA。前者省计算，后者保质量。

4. CSA2：沿三个维度同时压缩 ​

4.1 KV Cache 的三个乘法维度 ​

V4.1 技术报告把 KV 压缩拆成三个维度：

维度压缩对象代表技术效果
Entry 维度每个 KV entry 的“宽度”GQA、MLA、shared-KV MQA每 token 每层的字节数下降
Sequence 维度KV entry 的“长度”CSA、HCA、DSA top-k每 token 的 entry 数下降
Layer 维度KV entry 的“层数”CSA2 的 Full/Reindex/Reuse、CED需要独立存储 KV 的层数下降

过去的方案通常只压一个维度：

  • GQA/MQA 压 head 数，但序列维度仍是 O(N)O(N)O(N)；
  • MLA 压 latent 宽度，但每层仍要存自己的 KV；
  • SWA 压序列，但会丢失长程信息，通常还要一个全局分支；
  • 稀疏注意力（如 V3.2 的 DSA）减少“读多少”，但全量 KV 仍然要驻留；
  • 跨层复用（YOCO/YOIO/HySparse）分别在 KV 或 index 上做文章，但往往只覆盖一个维度。

CSA2 的野心是：把三个维度乘起来。

4.2 三种模式：Full、Reindex、Reuse ​

CSA2 的每一层被静态指定为三种模式之一：

模式main KVindexer KTop-K indices本层计算作用
Full自己生成自己生成自己算完整 CSA2 路径每组的“锚点”
Reindex复用最近 Full 层复用最近 Full 层自己重算只算 indexer Q + 重新打分允许选择随层变化
Reuse复用最近 Full 层复用最近 Full 层复用最近索引层只算 Q + attention大多数层，最省

三种模式都保留两样东西：自己的 global Q 和 自己的 SWA KV。这是 V4.1 在“省”和“表达力”之间的关键平衡：全局记忆可以共享，局部记忆和查询不能共享。

按论文配置数一下 40 层：

  • Encoder 18 个 CSA2 层，分成 3 组、每组 6 层：每组 1 层 Full + 5 层 Reuse → 3 Full + 15 Reuse；
  • Decoder 20 个 CSA2 层，分成 5 组、每组 4 层：第 1 组 1 层 Full + 3 层 Reuse；后 4 组每组 1 层 Reindex + 3 层 Reuse → 1 Full + 4 Reindex + 15 Reuse；
  • 合计：4 Full + 4 Reindex + 30 Reuse（另外 2 层是纯 SWA）。

也就是说，40 层里只有 4 层真正生成并存储 global KV（Encoder 3 层 + Decoder 1 层；后者按 CED 公式从 HL/2H_{L/2}H​L/2​​ 投影）；30 个 Reuse 层连 main KV、indexer K 和 top-k indices 都直接复用；另有 4 个 Reindex 层复用 KV，但要用自己的 indexer Q 重新打分。这是 890 B/token 的最大来源之一。

4.3 序列压缩：CSA2 比 CSA 更简单 ​

CSA2 的 Encoder 用 m=2m=2m=2，Decoder 用 m=1m=1m=1。这里 mmm 是压缩率：每 mmm 个 token 压成一个 main KV entry。Decoder 用 m=1m=1m=1 意味着不压序列，只靠跨层共享和 FP4 来省；Encoder 用 m=2m=2m=2 则把全局记忆的长度减半。

相比 V4 的 CSA，CSA2 做了三个简化：

  1. 去掉重叠压缩：CSA 的压缩率 mmm 会产生每个 entry 来自 2m2m2m 个原始 KV 的重叠窗口；CSA2 去掉重叠，每个 entry 只覆盖 mmm 个 token，实现更简单。
  2. 去掉绝对位置编码：CSA 在压缩时加入绝对位置嵌入；CSA2 去掉它，靠 RoPE 和后续注意力处理位置。
  3. indexer K 直接从 main KV 投影：不再走独立的压缩路径，减少一套参数和计算。

这些简化表面上“少了一点表达力”，但换来了更好的训练效率和更干净的推理 kernel。

4.4 稀疏选择：top-512 与分层 indexer ​

每个需要重新选 top-k 的 CSA2 层（Full 和 Reindex）都有一个轻量 indexer：用 indexer Q 给 main KV entry 打分，选出 top-512 个 entry，再让主注意力只读这 512 个 entry。这样 decode 时，主注意力的读取量固定在 512 个 main KV entry 加 128 个 SWA token，不随上下文长度增长。但 Full 层的 indexer 仍需扫描全部可见 main KV；只有 Decoder 中后续的 Reindex 层才受候选池限制（见下文）。

V4.1 还加了一个 Hierarchical Sparse Indexer，只用在 Decoder：

  • Decoder 的第一个 Full 层扫描全部可见 main KV，选出自己的 top-512，同时按块打分；
  • 它选出最多 2048 个 block、每块 8 个位置，构成一个最多 16,384 个候选位置的候选池；
  • 后续 Reindex 层只在这个候选池里重新打分，不再扫描全上下文；
  • Reuse 层直接复用最近索引层（Full 或 Reindex）的 top-k，连 indexer 都不跑。

这带来一个很重要的复杂度变化：Decoder 的第一个 Full 层仍然是全扫描，但后续 indexer 的每 query 成本与上下文长度无关。对于 1M 上下文，这能省掉大量重复的 indexer 计算。

关键认知：CSA2 不是“稀疏注意力”的同义词。稀疏注意力只减少“读多少”；CSA2 同时减少“存多少”（跨层共享 + 序列压缩）和“算多少”（index 复用）。这三件事必须一起做，才能把 KV 压到 890 B/token。

5. FP4 KV：4 bit 的工程学 ​

5.1 为什么是 MXFP4？ ​

V4.1 的 main KV 使用 MXFP4 格式：

  • 数值格式：E2M1，4 bit，能表示 0、±0.5、±1、±1.5、±2、±3、±4、±6 等有限档位；
  • 缩放因子：每个 16 通道共享一个 E4M3 scale（1 B）；
  • 不采用 NVFP4 的第二级 global scale，以简化 cache layout。

反量化可以写成：

x≈s⋅q,q∈E2M1,s∈E4M3x \approx s \cdot q, \qquad q \in \text{E2M1}, \quad s \in \text{E4M3} x≈s⋅q,q∈E2M1,s∈E4M3

其中 sss 每 16 个通道一个。这样做的好处是：存储时是 4 bit，计算时反量化回更高精度再做注意力，因此不需要硬件原生支持 FP4 矩阵乘，兼容性更好。

5.2 为什么可以去掉 global scale？ ​

FP4 的动态范围很窄，通常需要小心处理离群值。V4.1 论文给了一个很漂亮的界：

  • 训练中最大的 RMSNorm 权重幅度约为 1；
  • RMS 归一化后，512 维 KV latent 的 L2 norm 至多约为 512≈22.6\sqrt{512} \approx 22.6√​512​​​≈22.6；
  • RoPE 保持范数不变，所以旋转后每个通道的最大绝对值也不会超过约 22.6；
  • 实际训练中观测到的最大幅度约为 10。

而 E2M1 的最大值 6 乘以 E4M3 scale 的最大值 448，可表示到 6×448=26886 \times 448 = 26886×448=2688，远高于 22.6。因此去掉第二级 global scale 不会造成可测量的精度损失，却能简化布局、减少元数据。

5.3 为什么量化在 RoPE 之后？ ​

论文比较了“先量化再 RoPE”和“先 RoPE 再量化”：

  • 先量化再 RoPE 只有边际的精度提升，但 decode 时要多做一次 RoPE，增加开销；
  • 先 RoPE 再量化则可以直接把量化后的 cache 送给注意力 kernel。

最终选择 先 RoPE 再量化，因为精度差异很小，而推理路径更干净。

5.4 为什么 SWA KV 仍然是 FP8？ ​

V4.1 只把 main KV 压到 FP4，SWA KV 保持 FP8。原因是 SWA 对量化更敏感：它负责局部细粒度依赖，窗口只有 128，存储量有界，没必要为了省一点内存牺牲质量。

这也体现了一个原则：不是所有 KV 都值得用同一种精度。全局 KV 量大、可以粗；局部 KV 量小、需要细。

5.5 QAT 而不是 PTQ ​

FP4 main KV 不是训练完再量化的，而是在 post-training 阶段做 QAT。这样模型能在训练时适应 4 bit 的误差，而不是等到推理时才发现精度掉了。

关键认知：FP4 KV 的难点不在“把数变成 4 bit”，而在“让模型在 4 bit 下仍然正常工作”。QAT、scale 布局、量化位置、SWA 例外，缺一不可。

6.4 1M 上下文意味着什么？ ​

890 B/token × 1M = 890 MB。这仍然不是一个小数目，但已经从“一个请求打爆一张卡”变成“一张 80GB 卡可以同时放几十个请求的 KV”（忽略权重和激活）。对比之下：

  • V4-Flash 约 3.5 KB/token → 1M 约 3.5 GB；
  • 初代 V1 约 390 KB/token → 1M 约 390 GB。

这就是为什么 1M 上下文在 V4.1 上“可部署”，而在早期架构上只能停留在论文里。

关键认知：长上下文的第一性问题不是“注意力算得快不快”，而是“KV 放不放得下、搬不搬得动”。890 B/token 是把 1M 上下文从演示变成产品的前提。

7. 持久化 KV：把缓存当存储系统 ​

7.1 V4 的问题：SWA KV 占了近一半持久化缓存 ​

V4 的持久化 KV Cache 里有两类数据：

  • Global KV：CSA/HCA 压缩后的全局 KV，支持完整前缀复用；
  • SWA KV：每层最近 128 个 token 的局部 KV，不压缩。

问题在于：SWA KV 虽然每层只看 128 个 token，但它每层都有、且不压缩。V4 论文指出，按单位 token 计，SWA KV 的体积约为压缩后 CSA/HCA KV 的 8 倍；V4.1 报告在回顾 V4 部署时补充说，V4 只在 prompt 末尾和输出末尾两个位置保存 SWA 状态，在典型工作负载下，即便如此，它在持久化缓存里仍占了近一半容量。

更尴尬的是访问模式：

  • Global KV 有长尾复用价值，一个前缀可能几小时后还被再次命中；
  • SWA KV 只在当前会话的分钟级窗口内有用，会话结束或下一轮开始就“死了”。

把短期状态按长期缓存来存，既浪费 SSD，又拉低命中率。

7.2 V4.1 的做法：分层 + TTL + 有界重放 ​

V4.1 把两类 KV 彻底拆开：

缓存类型存什么位置精度生命周期未命中时
Global KVmain KV + indexer KHBM；持久化到 SSD/主机内存FP4至少 72 小时从持久化缓存加载，完整前缀复用
SWA KV最近 128 token 的局部 KVHBM；主机 DRAM 池FP8分钟级 TTLSWA Bounded Replay

几个关键数字：

  • SWA KV 不再写入持久化缓存，而是放在每台机器 10% 主机 DRAM 组成的分布式内存池里；
  • 这个池子的 TTL 只有分钟级，但周转很快，足以覆盖绝大多数活跃会话；
  • Global KV 仍然保证至少 72 小时 的持久化寿命。

这样，持久化 KV 的体积就变成：

  • 去掉 SWA KV：体积约减半；
  • Global KV 再压到 1/4：再缩小 4 倍；
  • 合计约 1/8。

7.3 SWA Bounded Replay：把“灾难性 miss”变成“轻微退化” ​

如果 SWA KV 被淘汰，最直接的做法是精确重算。但 SWA 的依赖是逐层累积的：要精确恢复第 lll 层的 SWA KV，需要从第 l−1l-1l−1 层的 SWA KV 推上来；要恢复所有层，理论上要重放 L×nwinL \times n_{\text{win}}L×n​win​​ 个 token。按 40 层、窗口 128 粗略估算，就是几千个 token 的前向，成本很高。

V4.1 的 SWA Bounded Replay 只重放最近 nwinn_{\text{win}}n​win​​ 个 token，并接受近似：

  • Encoder 侧：重放缓存前缀的最后 128 个 token，重新生成 SWA KV；已缓存的 global KV 直接复用，不重算、不覆盖；
  • Decoder 侧：每次 prefill 只重放 prompt 最后 128 个 token，把它们的 Encoder 输出过一遍 Decoder，得到首批 decode 需要的 SWA KV；这份 KV 不进入前缀缓存。

对于从位置 sss 开始的重放，查询 iii 的 SWA 注意力范围被截断为：

[max(s,i−W+1),i]\bigl[\max(s, i - W + 1),\; i\bigr] [max(s,i−W+1),i]

其中 W=nwin=128W = n_{\text{win}} = 128W=n​win​​=128。这显然不是精确的全局 SWA 状态，但论文实验显示质量下降可以忽略。为了进一步降低训练-推理错配，V4.1 在 post-training 阶段还模拟了同样的重放过程，让模型提前适应这种近似。

关键认知：V4.1 不是“消灭 cache miss”，而是“让 miss 变得便宜”。精确重算要几千 token，有界重放只要 128 token；这让“不持久化 SWA KV”从冒险变成合理。

8. 训练：45T token 与“从零稀疏” ​

8.1 预训练数据与视觉编码器 ​

V4.1 在 45T token 的多模态语料上预训练，文本与多模态的比例约为 7:1。数据管线有几个值得注意的点：

  • 过滤“信息增益有限”的模型生成内容，包括较弱模型的输出和低质量机翻；
  • 代码数据加入更新的开源仓库、commit、库和框架，覆盖更多编程语言；
  • 多模态数据以图文对、交错图文和领域数据为主，尽量用原始网页/PDF，而不是大规模合成；
  • 用 SmolVLM 做严格的质量评分，低质文档会被回收、重组；
  • 用改进的 best-fit packing，把 padding 率压到 10−410^{-4}10​−4​​ 以下。

视觉侧，DeepSeek-ViT 先用 SigLIP 的 sigmoid 对比损失在约 47B 图文对上预训练（分辨率限制在 224×224），再用一个 4B MoE LLM 做 236B token 的自回归微调（分辨率 544–1344），最后丢掉 LLM，只保留视觉编码器。

8.3 优化器：Muon + Sinkhorn ​

V4.1 的优化器组合很有 DeepSeek 特色：

  • Muon：用于语言骨干、Engram 投影、视觉-语言投影的线性权重；对 Q/K 使用 head-wise Muon，让不同 head 有不同的预条件器，适应注意力头的异质性；
  • AdamW：用于 RMSNorm、bias、scale 等非矩阵参数；
  • Sinkhorn-balanced momentum：用于 Engram embedding、token embedding、prediction head。它只用动量缓冲，不用 Adam 的二阶矩，因此大幅节省优化器状态内存；同时通过行/列归一化平衡 token 维和特征维的更新幅度。

Sinkhorn 更新的关键参数是 K=11K=11K=11、τ=10−3\tau=10^{-3}τ=10​−3​​、γ=0.18\gamma=0.18γ=0.18。论文说它在实践中优于 Adam，同时内存更省。对于 196B 参数的 Engram 模块，这不是小优化。

8.4 训练基础设施：为 CSA2 和超长序列改造 ​

V4.1 的训练基础设施有几个针对架构的改造：

  • CSA2 的 shadow indexer：共享 KV 的层可能被切到不同 pipeline stage，直接在 stage 间复用模块会破坏流水线。DeepSeek 在每个参与 stage 放一个轻量可执行副本，但保留单一逻辑 owner 负责优化和 checkpoint，stage 之间只同步参数和梯度。
  • Pipeline payload extension：当共享层跨 pipeline 边界时，把下游需要的中间表示和稀疏路由信息塞进已有的点对点通信，按 context parallelism 分区，避免额外复制。
  • Micro-batch 级共享状态管理：跟踪并发 micro-batch 的共享状态，在前向、激活重计算、反向之间协调生命周期；最后一个消费者用完后立即释放。
  • 多模态长序列优化：图像按 CP rank 做负载均衡分片，每张图只加载一次；RL rollout 只增量传输图像，并把 CPU 侧解码/预处理结果缓存到分布式文件系统。
  • Engram：embedding 表按行切分到专用 process group，优化器状态再分片；lookup 索引只依赖 token 序列，因此可以在 pipeline stage 开始前预取；FP8 存储；推理时可经 RDMA 从主机内存预取，训练时 embedding 预取与梯度传输则与视觉编码器计算重叠。

8.5 后训练：算法不新，数据/环境是护城河 ​

V4.1 的后训练遵循标准范式：SFT → RL → on-policy distillation（OPD）。论文明确说没有算法创新，实质变化主要在数据、环境和训练基础设施：

  • 把任务形式化为 (problem, environment, verification system) 三元组，用难度和正确性作为奖励，迭代训练模型自己构造更好的任务；
  • 通用 Agent 环境：内部员工/外部伙伴返回真实工具调用数据，构造 mocked tools，覆盖 SaaS、企业后台等接口；
  • Coding Agent 环境：内部/外部 coding session + 高 star GitHub 仓库；多个专用 Agent 协作完成“能否容器化、能否自动验证、任务起点、fail-to-pass/pass-to-pass 评估点、环境搭建、自测、去泄漏、打包镜像”；
  • DSec：生产级 sandbox 平台，支持百万级并发容器；用分片 + 放宽一致性调度、sub-NUMA 绑核、AppArmor/eBPF 隔离，并处理 Agent 的 reward hacking、删库、提权等行为；
  • 异步 RL：rollout 和训练同机分时，sample-level dispatch 保持并发；处理长度偏差和 off-policy；token 级中断，KV Cache 和 expert routing 按 token 粒度持久化，checkpoint 切换后可无缝续跑；
  • 大规模 OPD：40+ 个异构 teacher，支持全词表蒸馏，训练中可动态调整数据配比、并发限制和 active teacher。

8.6 DSpark：把 speculative decoding 也做成架构组件 ​

V4.1 在语言骨干预训练中去掉了 V3 的 MTP，改用 DSpark 做推测解码：

  • drafter 只有 3 个 Transformer block，SWA 窗口 128；
  • 一次前向并行给出 5 个 draft position 的 base logits；
  • 一个轻量 Markov head 建模 draft token 之间的依赖；
  • 一个 confidence head 预测每个位置的接受概率，估计前缀存活率；
  • 调度器结合 engine throughput 曲线，动态选择每个请求的验证长度，最大化系统级 token 吞吐。

DSpark 不是在预训练时和 backbone 一起训练的，而是在预训练后单独训练（backbone 冻结），post-training 时继续训练但不把梯度传回 backbone。这样它始终跟当前策略对齐，既能加速在线服务，也能加速 RL/OPD 的 rollout。

关键认知：V4.1 的训练不是“先设计模型，再想办法训”，而是从第一天就把稀疏选择、FP4 KV、SWA 重放、推测解码纳入训练目标。训练时模拟推理时的近似，是这套架构能落地的关键。

9. DeepSeek 的 KV Cache 优势：四层协同 ​

9.1 一条从 MLA 到 CSA2 的主线 ​

DeepSeek 不是从 V4.1 才开始压 KV 的。把几代模型连起来看，会发现一条非常清晰的主线：

代际注意力 / KV 关键机制结果
DeepSeek-V1（67B）GQA（8 个 KV head）KV 约 390 KB/token（图中为 389,120 B）
DeepSeek-V2MLA：低秩 latent 压缩 KVKV 减少 93.3%，最大生成吞吐 5.76×
DeepSeek-V3MLA + DeepSeekMoE + MTP + FP8671B 总参数、37B 激活，训练更稳
DeepSeek-V3.2MLA + DSA：lightning indexer + top-k128K 上下文，KV 约 48 KB/token；decode 读取量大幅下降，但全量 KV 仍驻留
DeepSeek-V4CSA/HCA + SWA + 混合精度1M 上下文；Pro 的 KV 仅为 V3.2 的 10%，Flash 为 7%（约 3.5 KB/token）
DeepSeek-V4.1CED + CSA2 + FP4 + SWA Bounded Replay890 B/token；global 1/4、persistent 1/8（对比 V4-Flash）

表中 V1–V4 的数字来自各代技术报告；V1、V3.2、V4-Flash 的 KV 对比值取自 V4.1 报告图 1(b)[1]。

这条主线说明：DeepSeek 的 KV 优势不是一次性的“灵光一现”，而是每一代都在同一组坐标轴上继续压。MLA 压宽度，CSA/HCA 压长度，CSA2 压层数，FP4 压精度，持久化缓存压体积和生命周期。

9.2 四层协同模型 ​

把 V4.1 的做法拆成四层，会更清楚：

层面做法代表技术解决的问题
表示层不再按 query head 逐份存 K/V：MLA 存低秩 latent，CSA2 存所有 head 共享的单份 512 维 main KVMLA、shared-KV MQAKV 的“宽度”
序列层每 mmm 个 token 压成一个 entry；top-k 稀疏读取CSA/HCA、CSA2、DSAKV 的“长度”和读取量
层级跨层共享 main KV / indexer K / top-k；Decoder KV 由 Encoder 投影CSA2 Full/Reindex/Reuse、CEDKV 的“层数”和 prefill 计算
系统层global/SWA 分层存储；SSD/主机 DRAM；TTL；有界重放；kernel 融合persistent KV、SWA Bounded Replay、FlashMLA/DeepGEMM/DeepSelect容量、带宽、寿命、miss 成本

这四层不是独立的，而是互相成就：

  • 没有 MLA 的低秩压缩或 shared-KV MQA 的单 head 共享，CSA 的每个 entry 会按 query head 数膨胀，跨层共享也省不下多少；
  • 没有 CSA2 的跨层共享，FP4 只能把 40 层的 KV 各压 4 倍，仍然不够；
  • 没有 FP4，4 个 Full 层的 KV 还是 FP8，890 B 会变成约 1.7 KB；
  • 没有 SWA Bounded Replay，去掉 SWA 持久化会导致昂贵的重算，系统层不敢这么设计；
  • 没有 FlashMLA/DeepGEMM/DeepSelect 等 kernel，Reuse 层“prefill 15 个、decode 11 个 kernel”的流程就跑不起来，理论节省也变不成吞吐。

9.3 和其他 KV 压缩思路对比 ​

方法压缩维度减少存储？减少读取？主要代价
MQA / GQAhead是是表达能力 / 质量
MLAhead / latent是是训练和实现复杂
SWA序列（局部）是是长程遗忘，需要全局分支
线性注意力 / SSM序列（状态）是是精确召回弱
KV 量化精度是是精度损失
稀疏注意力（DSA）读取否（全量 KV 仍在）是indexer 开销
跨层共享 KV（YOCO/HySparse）层是是层间表达耦合
跨层共享 index（YOIO）索引否（KV 仍全量）是路由共享限制表达
Offloading / PagedAttention存储层级部分（HBM 占用 / 碎片）否 / 部分带宽、延迟
CSA2 + CED + FP4 + Replay全部是是工程复杂度、近似风险

这张表想说明的是：单点技术都不稀奇，难的是把它们组合起来，并且让组合后的模型仍然能训练、能跑快、能保持质量。 DeepSeek 的“独”，更多是这种全栈协同和迭代深度，而不是“别人完全没想到”。

9.4 开源与工程透明度 ​

还有一层容易被忽略的优势：透明度。DeepSeek 不只放权重，还放技术报告、推理代码和 kernel：

  • V3.2 开源了 FlashMLA 的稀疏注意力 kernel[12]；
  • V4 开源了 CSA/HCA 的推理实现、DeepGEMM、DeepEP 等；
  • V4.1 在 Hugging Face 放出权重和模型卡[11]，报告详细描述了 Reuse Mode 下 prefill 15 个、decode 11 个 kernel 的流程、EPD 分离、持久化缓存管理[1]。

这让社区可以复现、适配、优化，也让 DeepSeek 的架构更容易成为事实标准。对于需要自部署的企业，这种透明度本身就是采用理由。

10. 对开发者的启示 ​

10.1 如果你通过 API 使用 ​

  • 保持前缀稳定：system prompt、工具 schema、长文档尽量放在会话前部，不要频繁改动；这样更容易命中持久化 KV 前缀缓存。
  • 长上下文不等于长记忆：1M 是容量，不是效果保证。关键信息仍应放在显眼位置，必要时做检索/摘要。
  • 用 reasoning effort 控成本：日常任务用 low/high，只有最难的任务用 max；论文显示收益主要集中在低到中等档位，继续提高 effort 的边际收益递减。
  • Agent 场景注意缓存命中：工具输出会快速膨胀上下文，尽量复用会话、减少重复 prefill。

10.2 如果你自部署 ​

  • 先算 KV 预算，再算权重：890 B/token 听起来很小，但 1M 上下文仍是 890 MB/请求；并发一上来，KV 会和权重抢 HBM。
  • 需要支持 FP4 dequant 的 kernel：V4.1 的 main KV 是 FP4 存储、反量化后计算；不是简单地把模型权重量化就能跑。
  • 准备分层存储：global KV 要能落 SSD/主机内存，SWA KV 要有主机 DRAM 池和 TTL；否则长会话的缓存命中率会很难看。
  • 关注稀疏 attention kernel：top-512 + SWA 128 的读取模式与 dense attention 不同，FlashMLA/DeepGEMM 这类 kernel 很关键。
  • 硬件规模：官方提到大规模部署需要 2k 卡 GPU 和存储集群[2]；V4.1 是“便宜”，但不是“单卡可跑”。

10.3 如果你在设计模型 ​

  • 把 KV 当成一等公民：不要等模型训完再想量化/稀疏；在架构阶段就决定 KV 的宽度、长度、层数和精度。
  • 非对称 prefill/decode 是值得探索的方向：输入重、输出轻的 Agent 负载，天然适合“prefill 只跑一半、decode 跑全量”的设计。
  • 跨层共享要解耦“存 KV”和“存 index”：CSA2 的 Full/Reindex/Reuse 三态，比“所有层共享一切”更灵活。
  • 训练时模拟推理近似：SWA 重放、FP4 QAT、分层 indexer 都在训练时模拟推理路径，避免 train-inference mismatch。
  • 缓存 miss 是可以设计的：与其追求 100% 命中，不如让 miss 的恢复成本有界；这是系统设计里很实用的一招。

10.4 一些需要保留的疑问 ​

  • 890 B/token 不含 SWA KV、权重和激活，不能拿它直接估算整机内存。
  • CSA2 的模式是静态分配的，不是按输入动态选择；对不同任务是否最优，论文没有展开。
  • 稀疏选择和 SWA 重放都是近似，论文自己把“选择错误”和“状态重建误差”列为 robustness boundaries（鲁棒性边界）。
  • FP4 KV 的精度在极端输入下是否稳定，需要更多独立评测。
  • Benchmark 是厂商报告：V4.1 在 DeepSWE、Terminal-Bench 2.1 等任务上很强，但在 Terminal-Bench 4.0 这类专家级科学任务上仍落后 Opus-5（31.2 vs 51.8）[1]。它不是“全面超越前沿”，而是“在大多数日常任务上极具性价比”。

11. 结语 ​

DeepSeek V4.1 Flash 是一篇典型的“系统论文”，只不过它披着模型发布的外衣。

它最重要的三个设计，都不是孤立的：

  1. CED 让 prefill 只跑 Encoder，把全局 KV 变成一次投影，换来近一半的 prefill 节省；
  2. CSA2 把 KV 压缩拆成 entry、sequence、layer 三个乘法维度，用 4 个 Full 层 + 4 个 Reindex 层 + 30 个 Reuse 层把层数成本摊薄；
  3. FP4 + SWA Bounded Replay + 分层持久化 把“存多少、放哪里、活多久、miss 了怎么办”变成一套完整的存储系统设计。

如果只看单个技术点，MLA、稀疏注意力、KV 量化、跨层共享、prefix caching 都不是 DeepSeek 首创。但把这些东西同时做进一个 552B MoE、1M 上下文、原生多模态、还能开源部署的模型里，并且让每一代都在同一组坐标轴上继续压，这才是 DeepSeek 真正的 KV Cache 优势。

用一句话收尾：

长上下文的竞争，表面上是“谁能读得更长”，本质上是“谁能把记忆存得更小、搬得更快、丢得更便宜”。V4.1 Flash 的 890 B/token，就是对这个问题的回答。
